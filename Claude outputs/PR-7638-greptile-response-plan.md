## 3. Design tweaks (beyond the review)

1. **Holdouts (#12): keep the decision, drop the side effect.** Instead of omitting the holdout force rule for the whole feature, AND its condition with `$not` of the OR of the overrides' compiled filter conditions. QA-matching users skip the holdout; everyone else keeps it. An override with no attribute/Saved-Group filter matches everyone, so the holdout drops — same as today, but only when unavoidable (connection and project filters are already resolved per connection before this point). Reply to the review with this reasoning.

2. **Make "first match wins" true for visual experiments too (#18).** Same trick: AND each later override's condition with `$not` of the earlier overrides' filters. One helper, `exclusionOfEarlierOverrides(overrides, index, savedGroupStrategy)`, shared by the feature-rule holdout (tweak 1) and the auto-experiments builder. Reordering then means the same thing for a Feature Flag draft and a visual draft, and the UI copy needs no caveat.

3. **Stop skipping refreshes from lifecycle hooks (hardening, optional).** Traced on 11/09: the status-change, archive and delete paths all refresh the right environments via `oldPayloadKeys ∪ newPayloadKeys`, so this is not a correctness fix. It still removes a dependency on `getPayloadKeys` internals, and refreshes merge per request, so it costs nothing. Do it if commit 2 is open anyway; drop it if the diff is getting large.

4. **Revert "rule id = override id" for dev tools.** Dev tools look rule ids up against the feature's rules; an `eqo_…` id matches nothing and may render worse than the stem id. The `::qa` suffix already marks the rule. Keep the stem id; add explicit metadata only after confirming every SDK ignores an unknown rule field.

5. **Pass `includeRuleIds` explicitly** to `applyQaOverrideToRule` instead of inferring it from `rule.id` being set.

6. **Do PR F (Live / QA exposures toggle on the Health tab) in this PR.** The back-end `exposureSource` parameter exists; the UI is small; without it the `::qa` data is invisible and the "set an override, hit the app, watch the exposure appear" loop doesn't exist.

### The `::qa` key guard (#8)

Greptile's point is the team's API-compatibility rule, not a bug: the REST API accepts any `trackingKey`, so rejecting `*::qa` is a (theoretical) breaking change.

- **Recommended:** keep the guard for keys created or edited through the app, skip it on the REST path (`createExperiment`/`updateExperiment` are shared; gate the assertion on the context being a dashboard request). Keep the past-experiments discovery filter: a warehouse key that literally ends in `::qa` is far more likely ours than a customer's, and hiding it from _import_ is low-impact. Reply explaining the suffix can't be generated by the app, so the guard protects dashboard users from a confusing collision while the API stays additive.
- Alternatives: drop the guard entirely (a dashboard user could then collide with QA data), or declare a versioned breaking change with the Platform Squad (not worth the ceremony).

## 4. API ergonomics

The PR doesn't touch the public REST API; this is the internal `/qa-overrides` surface the UI (and later REST) sit on. In order of impact:

- **`filters` is required on create.** Make it optional and default it server-side, so the common case is `{ environment, assignment }`.
- **Environment is immutable.** Changing it means delete + recreate, and the modal locks the field on edit. Allow it: validate the new environment, refresh both old and new. Decide before Gabe designs the edit state.
- **Status is computed client-side.** Return `status: "active" | "waiting"` and `waitingOn: [{ featureId, reason }]` per override from `GET /experiment/:id` and `GET /sdk-connection/:id`. One source of truth, the connection page can show status (it can't today), and it's what a REST endpoint would want.
- **Error messages name ids.** Use names, and for the production case say which setting to flip.
- **Reorder requires the full list.** Also accept `order` on `PUT /:id`; keep the full-list endpoint for drag-reorder.
- **Writes aren't hydrated.** `POST`/`PUT` return the bare override and the UI refetches. Return `{ override, sdkConnections }` from writes too.
- **Public REST API: not in this PR.** If customers will drive QA from CI, `/api/v1/experiments/:id/qa-overrides` is the obvious next ask; the validators are already in `shared`. Shape the responses above so it's a straight lift.
