### qa_editor × Config (`purchase-flow`)
- offered (⋮ header menu, unlocked): Edit information, Audit history, **Lock…**, **Enable experiment guard**, Archive. No Delete (correct — no FlagsDelete).
- offered (Overview, live rev 1): New Draft, per-field Edit + per-field ⋮, Add field, Add Config mixin, Add override Config, per-key "+ Override", Form/JSON/Resolved tabs
- offered (Review & Publish, live rev 1): **Roll back DISABLED** with an amber crossed-circle blocker "You don't have permission to revert this config." — correct colour and correct atom
- offered (Review & Publish, draft rev 2 `changes-requested`): amber "Locked at v1. Unlock to publish." (correct colour), comment composer, sidebar ⋮. No Approve / Request changes (correct).
- verified by clicking: **Lock SUCCEEDED immediately** for a persona holding only draft+publish. Badge became "Locked · v1"; every edit affordance (New Draft, all Edit buttons, Add field, Add Config mixin, Add override Config, Edit information, Archive) disappeared; ⋮ collapsed to Audit history / Unlock… (disabled) / Enable experiment guard. Hovering Unlock… shows "You don't have permission to unlock this Config."
- expected: authors + lands changes; NOT approve, NOT archive/delete
- verdict: BUG
- detail:
  - **B1 (confirmed, medium) — Config Lock is a live governance write gated on the *draft* atom, and is one-way for anyone who can perform it.** `pages/configs/[cfgid].tsx:1584` renders `Lock…` under `canDraft`, applies immediately with no draft staging, whereas `Unlock…` at `:1596` is `disabled={!canBypassApproval}`. Net effect: qa_editor (and qa_drafter — see that cell) can freeze all publishing on a Config and cannot undo it. Requires an admin/bypass holder to recover.
  - Scheduled publish ("Automatically publish on a specific date" + "Lock edits to this draft") is offered to the editor while the draft is in `changes-requested`. Whether the scheduler re-checks approval at fire time is NOT verified — see "unverified / needs checking".
  - **B2 (confirmed, low/medium) — Feature vs Config inconsistency on Roll back.** On a Feature the editor gets an enabled Roll back that opens a draft-only Revert modal; on a Config the identical persona is blocked outright. Cause: `components/Reviews/Feature/ReviewAndPublish.tsx:1270` uses `canManageDrafts || canRevertFeature(...)` while `components/Revision/ReviewAndPublishTab.tsx:528` uses `canRevertEntity ?? canEditEntity` (revert atom alone). One of the two is wrong; see Summary for why this is not a small fix.
