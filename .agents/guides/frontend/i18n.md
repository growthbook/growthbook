# Front-end Translations (Lingui)

## Overview

The front-end uses [Lingui](https://lingui.dev). English is the source language and the default. Code marks user-facing strings, `lingui extract` collects them into one catalog per language at `packages/front-end/locales/{locale}/messages.po`, and Next compiles each `.po` file when it is imported. Commit the `.po` files; nothing compiled is committed.

Pages move over gradually. Unmarked text stays English in every language.

## Marking strings

- **JSX text:** `<Trans>` from `@lingui/react/macro`.

  ```tsx
  import { Trans } from "@lingui/react/macro";

  <Trans>
    Password reset link sent to <strong>{email}</strong>.
  </Trans>;
  ```

- **Strings in a component** (props, `aria-label`, toasts): `t` from `useLingui()` in `@lingui/react/macro`. When `t` is used inside `useMemo`, `useCallback` or `useEffect`, add `t` to the dependencies.

  ```tsx
  const { t } = useLingui();
  <Field label={t`Email Address`} />;
  ```

- **Data defined outside a component** (nav config, option lists): `msg` from `@lingui/core/macro` makes a `MessageDescriptor`. Resolve it where it renders with `i18n._()` from `useLingui()`. `components/Layout/sidebarNav.ts` is the example.

  ```tsx
  const links = [{ name: msg`Feature Flags`, href: "/features" }];
  // in the component
  const { i18n } = useLingui();
  <Link href={link.href}>{i18n._(link.name)}</Link>;
  ```

- **Plurals:** `<Plural value={n} one="# experiment" other="# experiments" />` from `@lingui/react/macro`.

Rules:

- Never import `t` from `@lingui/core/macro`. It uses Lingui's global instance, which is never activated; `LocaleProvider` owns the active one.
- Keep variables inside the message (`<Trans>Sent to {email}</Trans>`), never concatenate translated pieces. Word order differs between languages.
- Don't mark user data (entity names, keys, ids), messages returned by the back-end, or product names such as GrowthBook.
- A message's id is a hash of its English text. Changing English copy creates a new message that needs translating in every language.

## Catalog workflow

1. Mark the strings.
2. `pnpm --filter front-end lingui:extract` adds new messages to every catalog and removes unused ones.
3. Fill every new empty `msgstr` in each language. `#:` lines show which file uses a message.
4. `pnpm --filter front-end lingui:check` extracts, then compiles with `--strict`, which fails on any missing translation.

Commit the `.po` changes with the code that needs them.

## Adding a language

Add the code in three places, then extract and translate:

- `locales` in `packages/front-end/lingui.config.js`
- `supportedLanguages` and `languageNativeLabels` in `services/locale.ts`
- `catalogLoaders` in `services/LocaleProvider.tsx`

## Runtime

- `LocaleProvider` (`services/LocaleProvider.tsx`) wraps the app. The server render and first client render are English; the saved choice (`localStorage` key `gb_ui_locale`) is applied after mount, so hydration matches.
- The English catalog ships with the app. Other catalogs load on demand, and the UI keeps the current language until the next one arrives. `<html lang>` follows the active language.
- Tests that render a component using `<Trans>` or `useLingui()` pass `{ wrapper: I18nTestProvider }` (from `test/I18nTestProvider.tsx`) to `render`.
- `useLocale()` returns `{ language, setLanguage }`. The picker is `components/Layout/LanguageMenu.tsx`, in both top navs and on the login screen.

## Build setup

- Macros compile with `@lingui/swc-plugin` (`experimental.swcPlugins` in `next.config.js`) and, in Vitest, with `@lingui/vite-plugin`.
- The SWC plugin has to match the `swc_core` inside Next. Check [plugins.swc.rs](https://plugins.swc.rs) before upgrading Next or the plugin; a mismatch fails the build while loading the plugin.
- `.po` files compile through `@lingui/loader`, set up for both Turbopack and webpack in `next.config.js`.
- `types/jsx.d.ts` lets `<Trans>`, which returns a `ReactNode`, type-check with `@types/react` 18.0. Delete it once the front-end is on `@types/react` 18.2.8 or later.
