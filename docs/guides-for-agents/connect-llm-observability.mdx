## TL;DR

Connect an existing, self-hosted Langfuse v3 or Postgres-backed Arize Phoenix installation to one GrowthBook experiment. GrowthBook assigns a reviewed prompt or configuration; the application adds that assignment to the root trace; GrowthBook queries the tracing database for exposures and outcomes. The implementation preserves the current behavior as a local fallback and keeps each user's assignment separate from concurrent requests.

Start with the complete local fixture below. It uses the actual SDKs, synthetic requests, and an in-memory trace exporter, with no model bill or remote data writes. Then obtain the operator's authorization to configure an isolated staging experiment, export traces, and connect the database. A passing local test is the foundation; the integration is operationally verified only after a fresh staging trace and its metric appear in GrowthBook, failure handling and rollback work, and production measurement has a clean data boundary.

_This guide is optimized for AI coding agents, and it is recommended that you hand it off to your agent of choice for implementation._

## Task and scope

The bounded job is to connect an existing traced Node.js service to GrowthBook's experiment analysis. It is not an instruction to install an observability platform, migrate a database, or redesign an LLM application. The canonical implementation uses TypeScript, one shared `GrowthBookClient`, one scoped instance per request, and either a Langfuse or Phoenix root adapter. Preserve the service's existing authentication, provider integration, retry policy and instrumentation when adapting it.

The observable chain is:

```text
Stable application identity
  -> GrowthBook experiment assignment
  -> root trace tagged gb.exp:<experimentKey>=<variationKey>
  -> trace/observation/annotation rows in the tracing database
  -> GrowthBook exposure query and fact metrics
```

GrowthBook reads the tracing database; this path does not populate raw trace tables inside GrowthBook. The built-in trackers are beta and target vendor database schemas. Treat an upgrade of either tracing platform as a reason to retest generated SQL, even when application instrumentation has not changed. See the [LLM tracing integration](/integrations/llm-tracing), [Langfuse tracker](/event-trackers/langfuse), and [Phoenix tracker](/event-trackers/phoenix).

## Use this guide when

- Langfuse is self-hosted on the v3 server schema, with its ClickHouse database available for authorized read-only queries; or Phoenix stores traces in Postgres.
- Your application already has a stable opaque user identifier, an existing control behavior, and a working tracing path.
- An operator can create an isolated staging experiment and give GrowthBook read access to the required tracing tables.
- You can record at least one meaningful outcome and preserve the same identifier semantics from assignment through analysis.

Langfuse's server version and its JavaScript SDK version are different version lines. In particular, the [SDK v5-to-v6 migration](https://langfuse.com/docs/observability/sdk/upgrade-path/js-v5-to-v6) requires a newer Langfuse server for SDK v6. Do not install unpinned current SDKs into a v3 server integration. Use the exact tested package versions in the fixture and recheck compatibility against your server before updating them.

Langfuse Cloud has a separate route: [export to blob storage](https://langfuse.com/docs/api-and-data-platform/features/export-to-blob-storage), load or expose those objects in your own supported warehouse, and adapt the fact-table SQL. Export is not itself the warehouse-loading step. That route, Langfuse server v4, Phoenix on SQLite, hosted Phoenix/Arize AX, Braintrust, and LangSmith are outside this implementation. Report the discovered stack and the missing implementation path instead of improvising a migration. This scope statement does not claim those tools can never work with GrowthBook.

## End state and authority boundary

The local implementation is complete when actual SDK tests show stable assignment, correct root attributes, no cross-request tags, no false exposure on the local control bypass, and closed error spans. The staging integration is complete when a fresh request made inside the analysis window is visible both in the tracing database and in the right GrowthBook variation, with a known outcome metric attached.

Production readiness additionally needs reviewed goal/guardrail definitions, an isolated production dataset, a tested control switch, and an owner for schema and SDK upgrades. One synthetic request proves data flow, not statistical power, measured lift, or the accuracy of a model evaluator.

Approval is action-specific. An authorization to edit this repository does not create database roles or launch a production experiment. Prepare the resource names, environment/project filters, proposed changes and readback steps for the operator. Human-only UI steps are legitimate parts of the workflow; identify exactly what evidence the operator must return before continuing.

## Inspect the repository and choose the contract

Run discovery in the application repository, not a guessed project directory. These commands inspect files and dependencies; they do not reveal environment values:

```bash
node --version
npm --version
npm ls --depth=0
rg -n 'GrowthBookClient|createScopedInstance|tracingPlugin|trackingCallback' src test tests
rg -n 'startActiveObservation|startActiveSpan|LangfuseSpanProcessor|phoenix-otel|OITracer' src
```

Use the repository's actual source directories and package manager when they differ. Missing directories are discovery findings, not a reason to create a second application. Inspect variable _names_ in the configuration schema and secret manager references. Never print an environment dump or paste connection strings into a receipt.

Record the tracing server version, database backend, Node/runtime constraints, installed SDK versions, existing OpenTelemetry provider, root-span creation point and exporter shutdown behavior. Find the authenticated opaque user and conversation IDs already used by the tracer. Determine whether HTTP auto-instrumentation starts a root span before your handler and which span the tracing backend persists as the root.

Both fixture adapters start a separate LLM trace from `ROOT_CONTEXT`. Use that boundary when the LLM workflow should have its own trace and its own measurement root. If your service needs to keep the LLM work in an existing HTTP or distributed trace, preserve that context and adapt the instrumentation to attach identity and assignment tags to the root that the tracing backend actually persists. Changing the parent context alone leaves the tags on the handler's child span. Confirm the tagged root in the tracing backend and the assignment query.

Choose one randomization unit before implementing. This reference uses `user_id`, with the identical value in GrowthBook attributes and the tracer's user field. A session-based experiment must instead evaluate with a stable session attribute and choose the matching assignment query. Per-trace assignment needs a trace ID established before evaluation. Do not change units halfway through a phase, and do not infer a logged-in user ID from an email address or invent an anonymous ID for the example.

Write a small contract in the implementation PR: feature key, experiment tracking key, variation keys, prompt/config values, assignment attribute, tracer project, analysis data source, and local fallback. These are different identifiers. The feature key can select a prompt label while the experiment key names the assignment recorded in a trace. Do not assume that the string feature value and variation key are equal.

Keep experiment keys free of `=`. The tracing plugin skips such keys. Validate the complete final tag and opaque identifiers against the tracer's documented limits: [Langfuse tags](https://langfuse.com/docs/observability/features/tags) and its [attribute API](https://js.reference.langfuse.com/interfaces/_langfuse_tracing.PropagateAttributesParams.html) specify 200-character limits for tags, user IDs and session IDs. Keep baggage propagation off unless the application's cross-service header policy explicitly permits it. A missing tag can be an input-validation problem as well as a tracing problem.

### Choose where the metrics will live

A GrowthBook experiment reads its metrics from one data source. If business events and tracing tables are queryable from the same database, add the tracker resources to that existing data source. If they live in separate databases that cannot query one another, decide whether this experiment measures tracing outcomes alone or needs a separate warehouse integration. Do not imply GrowthBook will join arbitrary data sources during experiment analysis.

Exposure inferred from traces includes only requests that produced those traces. If a treatment changes whether tracing or the LLM call happens, the resulting population may depend on assignment. Sampling, dropped exports and provider retries can also change the observed population. Establish equivalent collection behavior across variations and compare source requests with observed traces before using the results for a product decision.

### Choose the prompt and fallback boundary

Keep current behavior as the local default. The reference fixture maps a small set of reviewed labels to synthetic prompts; no prompt registry or model service is required to prove instrumentation. In your service, the selected value can retrieve a versioned prompt from the existing registry or select a reviewed configuration in code.

Validate the experiment payload and allowed values before launch. By default, the fixture serves `production` when an assigned value is invalid or an assignment tag exceeds 200 characters. It keeps valid tags from the original assignment and omits oversized tags. This preserves an identifiable experiment assignment when the request serves control. An omitted assignment tag leaves a gap in trace-derived exposures, so monitor that gap alongside fallback counts before interpreting experiment results.

The receipt records the served label as `value`, a recognized assigned label as `assignedValue` when available, and valid original tags as `tags`. A `fallback` carries a fixed `reason` and `missingTraceExposure` flag. The root trace records sanitized diagnostics in `growthbook.configuration_error`, `growthbook.control_fallback`, and `growthbook.trace_exposure_missing`, with `ERROR` status for the configuration fault. The model span reports the actual provider outcome. Keep raw feature values, oversized tags, and provider errors out of these diagnostics.

Set `failOnInvalidConfiguration: true` on `runObservedRequest` when an invalid assignment should fail the request during validation. On a configuration failure in this mode, the fixture closes the diagnostic root before reaching the model call. Prompt retrieval and provider failures follow the application's normal error handling.

The local rollback switch must bypass experiment evaluation before collecting tags. A warm SDK can still contain previously loaded rules during a connection outage; a fetch timeout alone does not guarantee that a running process switches to control. Prove both cold-start fallback and the local bypass with a cached experiment present. Use the [Node SDK lifecycle](/lib/node) when adapting refresh and shutdown behavior.

```ts
import {
  GrowthBookClient,
  type FeatureApiResponse,
} from "@growthbook/growthbook";
import { getTracingTags, tracingPlugin } from "@growthbook/growthbook/plugins";

export const FEATURE_KEY = "support-prompt";
export const STAGING_EXPERIMENT_KEY = "llm-observability-staging-v1";
export type Treatment = "production" | "candidate";
export const STAGING_VARIATION_KEYS = {
  production: "0",
  candidate: "1",
} as const;
export type FeatureSchema = { "support-prompt": Treatment };
export type ExperimentClient = GrowthBookClient<FeatureSchema>;

// One client per process. The CLI sets an offline payload; real services call init once.
export function createExperimentClient(
  options: {
    apiHost?: string;
    clientKey?: string;
  } = {},
): ExperimentClient {
  return new GrowthBookClient<FeatureSchema>({
    ...options,
    plugins: [tracingPlugin()],
  });
}

export function requireIdentifier(value: string, name: string): void {
  if (!value || value.trim() !== value || value.length > 200) {
    throw new Error(
      `${name} must be an existing nonempty identifier of at most 200 characters`,
    );
  }
}

export function selectTreatment(
  client: ExperimentClient,
  userId: string,
  experimentsEnabled: boolean,
): {
  value: Treatment;
  tags: string[];
  source: string;
  validationError?: string;
} {
  requireIdentifier(userId, "userId");
  // This bypass works even if a cached remote payload still contains the experiment.
  if (!experimentsEnabled)
    return { value: "production", tags: [], source: "local-bypass" };
  const scoped = client.createScopedInstance({
    attributes: { user_id: userId },
  });
  const result = scoped.evalFeature(FEATURE_KEY);
  if (result.value !== "production" && result.value !== "candidate") {
    if (result.source === "experiment") {
      // Keep the assignment and surface the invalid config inside the tagged root.
      // Do not erase failed treatment requests from the experiment denominator.
      return {
        value: "production",
        tags: [...getTracingTags(scoped)],
        source: "invalid-assigned-value",
        validationError: "invalid_assigned_value",
      };
    }
    return {
      value: "production",
      tags: [],
      source: "invalid-or-missing-value",
    };
  }
  return {
    value: result.value,
    tags: [...getTracingTags(scoped)],
    source: result.source,
  };
}

// Synthetic SDK response, not a REST API creation payload. Never publish this fixture.
export function makeTestPayload(
  weights: [number, number] = [0.5, 0.5],
): FeatureApiResponse {
  return {
    features: {
      [FEATURE_KEY]: {
        defaultValue: "production",
        rules: [
          {
            key: STAGING_EXPERIMENT_KEY,
            hashAttribute: "user_id",
            variations: ["production", "candidate"],
            weights,
            coverage: 1,
            hashVersion: 2,
            meta: [
              { key: STAGING_VARIATION_KEYS.production },
              { key: STAGING_VARIATION_KEYS.candidate },
            ],
          },
        ],
      },
    },
  };
}
```

#### `src/telemetry.ts`

```ts
import { context, trace } from "@opentelemetry/api";
import { AsyncLocalStorageContextManager } from "@opentelemetry/context-async-hooks";
import { InMemorySpanExporter } from "@opentelemetry/sdk-trace-base";
import { LangfuseSpanProcessor } from "@langfuse/otel";
import { NodeTracerProvider } from "@opentelemetry/sdk-trace-node";
import { setLangfuseTracerProvider } from "@langfuse/tracing";

export function startOfflineTelemetry() {
  const exporter = new InMemorySpanExporter();
  // The real processor copies Langfuse propagated attributes onto spans. A plain
  // SimpleSpanProcessor would export Langfuse roots without the tags under test.
  const processor = new LangfuseSpanProcessor({
    exporter,
    exportMode: "immediate",
    mediaUploadEnabled: false,
    shouldExportSpan: () => true,
    environment: "offline-synthetic",
  });
  const provider = new NodeTracerProvider({ spanProcessors: [processor] });
  const contextManager = new AsyncLocalStorageContextManager();
  provider.register({ contextManager });
  setLangfuseTracerProvider(provider);
  return {
    exporter,
    provider,
    async shutdown() {
      await provider.forceFlush();
      await provider.shutdown();
      contextManager.disable();
      context.disable();
      trace.disable();
    },
  };
}
```

#### `src/adapters.ts`

```ts
import {
  context,
  ROOT_CONTEXT,
  SpanStatusCode,
  trace,
} from "@opentelemetry/api";
import { propagateAttributes, startActiveObservation } from "@langfuse/tracing";
import {
  getAttributesFromContext,
  setSession,
  setTags,
  setUser,
} from "@arizeai/phoenix-otel";

export type TraceIdentity = {
  userId: string;
  sessionId: string;
  tags: string[];
};
export type CompletionResult = {
  text: string;
  model: string;
  synthetic?: boolean;
  inputTokens?: number;
  outputTokens?: number;
};
export interface RootAdapter {
  runRoot<T>(identity: TraceIdentity, work: () => Promise<T>): Promise<T>;
  runModel(work: () => Promise<CompletionResult>): Promise<CompletionResult>;
}

export class LangfuseRootAdapter implements RootAdapter {
  runModel(work: () => Promise<CompletionResult>): Promise<CompletionResult> {
    return startActiveObservation(
      "model-call",
      async (generation) => {
        try {
          const result = await work();
          generation.update({
            model: result.model,
            metadata: { synthetic: result.synthetic ?? false },
            usageDetails: {
              ...(result.inputTokens === undefined
                ? {}
                : { input: result.inputTokens }),
              ...(result.outputTokens === undefined
                ? {}
                : { output: result.outputTokens }),
            },
          });
          return result;
        } catch (error) {
          generation.update({ level: "ERROR", statusMessage: "model_failed" });
          trace
            .getActiveSpan()
            ?.setStatus({
              code: SpanStatusCode.ERROR,
              message: "model_failed",
            });
          throw error;
        } finally {
          generation.end();
        }
      },
      { asType: "generation", endOnExit: false },
    );
  }

  runRoot<T>(identity: TraceIdentity, work: () => Promise<T>): Promise<T> {
    // This boundary intentionally creates a separate LLM trace, not a child of HTTP spans.
    return context.with(ROOT_CONTEXT, () =>
      propagateAttributes(identity, () =>
        startActiveObservation(
          "support-reply",
          async (observation) => {
            try {
              return await work();
            } catch (error) {
              observation.update({
                level: "ERROR",
                statusMessage: "request_failed",
              });
              const span = trace.getActiveSpan();
              span?.setStatus({
                code: SpanStatusCode.ERROR,
                message: "request_failed",
              });
              // Avoid copying arbitrary provider errors, credentials, or user input into telemetry.
              span?.recordException(new Error("request_failed"));
              throw error;
            } finally {
              observation.end();
            }
          },
          { endOnExit: false },
        ),
      ),
    );
  }
}

export class PhoenixRootAdapter implements RootAdapter {
  runModel(work: () => Promise<CompletionResult>): Promise<CompletionResult> {
    return trace.getTracer("growthbook-llm-reference").startActiveSpan(
      "model-call",
      {
        attributes: {
          ...getAttributesFromContext(context.active()),
          "openinference.span.kind": "LLM",
        },
      },
      async (span) => {
        try {
          const result = await work();
          span.setAttributes({
            "llm.model_name": result.model,
            metadata: JSON.stringify({ synthetic: result.synthetic ?? false }),
            "llm.token_count.prompt": result.inputTokens,
            "llm.token_count.completion": result.outputTokens,
          });
          if (
            result.inputTokens !== undefined &&
            result.outputTokens !== undefined
          ) {
            span.setAttribute(
              "llm.token_count.total",
              result.inputTokens + result.outputTokens,
            );
          }
          return result;
        } catch (error) {
          span.setStatus({
            code: SpanStatusCode.ERROR,
            message: "model_failed",
          });
          throw error;
        } finally {
          span.end();
        }
      },
    );
  }

  runRoot<T>(identity: TraceIdentity, work: () => Promise<T>): Promise<T> {
    let ctx = setUser(ROOT_CONTEXT, { userId: identity.userId });
    ctx = setSession(ctx, { sessionId: identity.sessionId });
    ctx = setTags(ctx, identity.tags);
    return context.with(ctx, () =>
      trace.getTracer("growthbook-llm-reference").startActiveSpan(
        "support-reply",
        {
          // A plain OTel tracer does not automatically copy OpenInference context attributes.
          attributes: {
            ...getAttributesFromContext(ctx),
            "openinference.span.kind": "CHAIN",
          },
        },
        async (span) => {
          try {
            return await work();
          } catch (error) {
            span.setStatus({
              code: SpanStatusCode.ERROR,
              message: "request_failed",
            });
            span.recordException(new Error("request_failed"));
            throw error;
          } finally {
            span.end();
          }
        },
      ),
    );
  }
}
```

#### `src/application.ts`

```ts
import { SpanStatusCode, trace } from "@opentelemetry/api";
import {
  type ExperimentClient,
  requireIdentifier,
  selectTreatment,
  type Treatment,
} from "./experiment.js";
import type { CompletionResult, RootAdapter } from "./adapters.js";

export interface PromptResolver {
  resolve(label: Treatment): Promise<string>;
}
export interface ModelProvider {
  complete(input: {
    prompt: string;
    requestId: string;
  }): Promise<CompletionResult>;
}

export async function runObservedRequest(input: {
  client: ExperimentClient;
  adapter: RootAdapter;
  prompts: PromptResolver;
  model: ModelProvider;
  userId: string;
  sessionId: string;
  requestId: string;
  experimentsEnabled: boolean;
  failOnInvalidConfiguration?: boolean;
}) {
  requireIdentifier(input.sessionId, "sessionId");
  const selection = selectTreatment(
    input.client,
    input.userId,
    input.experimentsEnabled,
  );
  // Keep valid assignment tags intact. Changing an overlong tag would change
  // the experiment or variation key used in analysis.
  const tags = selection.tags.filter((tag) => tag.length <= 200);
  const omittedAssignmentTag = tags.length < selection.tags.length;
  const reason =
    selection.validationError ??
    (omittedAssignmentTag
      ? "experiment_tag_exceeds_200_characters"
      : undefined);
  const fallback = reason
    ? {
        reason,
        missingTraceExposure: omittedAssignmentTag || tags.length === 0,
      }
    : undefined;
  const value = fallback ? "production" : selection.value;
  // Evaluation and the tag snapshot happen before opening the actual LLM root.
  const result = await input.adapter.runRoot(
    {
      userId: input.userId,
      sessionId: input.sessionId,

          "growthbook.trace_exposure_missing": fallback.missingTraceExposure,
        });
        root?.setStatus({
          code: SpanStatusCode.ERROR,
          message: fallback.reason,
        });
        if (input.failOnInvalidConfiguration) throw new Error(fallback.reason);
      }
      const prompt = await input.prompts.resolve(value);
      return input.adapter.runModel(() =>
        input.model.complete({ prompt, requestId: input.requestId }),
      );
    },
  );
  // These are safe diagnostic fields, not an exposure event or an experiment result.
  return {
    value,
    assignedValue:
      selection.source === "experiment" ? selection.value : undefined,
    tags,
    source: selection.source,
    fallback,
    userId: input.userId,
    sessionId: input.sessionId,
    text: result.text,
  };
```

```ts
function selfHostedUrl(name: string, description: string): string {
  const value = required(name);
  const invalidUrl = () =>
    new SetupError(

    rules?.length !== 1 ||
```

## Failure injection and troubleshooting

Run these drills in the local fixture or isolated staging system. Capture actual output and the last verified boundary; a checklist with unchecked assertions is not an execution receipt.

| Drill                                | Expected observation                                                          | Do not conclude                                               |
| ------------------------------------ | ----------------------------------------------------------------------------- | ------------------------------------------------------------- |
| No experiment/default-only payload   | Control behavior, normal trace, no assignment tag                             | That the tracker can infer an experiment from a default value |
| Cold configuration fetch failure     | Local control with no invented assignment                                     | That a warm cached treatment disappears automatically         |
| Local bypass with cached rules       | Control, no experiment evaluation/tag                                         | That stopping analysis alone changed SDK traffic              |
| Two users concurrently               | Each root has only its own tag and identity                                   | That a global mutable tag list is safe                        |
| Invalid assigned value               | Control response, original valid assignment and configuration diagnostic      | That the assigned treatment ran                               |
| Oversized assignment tag             | Control response and missing-exposure diagnostic. The oversized tag is absent | That the tracker can recover the omitted assignment           |
| Strict validation failure            | Closed diagnostic root and no model call                                      | That production requests use strict validation by default     |
| Missing prompt or provider rejection | Ended error root; failure preserved                                           | That missing failed spans mean zero error rate                |
| Missing root attributes              | Database and exposure checks fail visibly                                     | That a correctly tagged child is sufficient                   |
| Export/collector outage              | Application behavior bounded; export failure visible                          | That local span completion means database persistence         |
| Database schema upgrade              | Query previews rerun before trusting metrics                                  | That a successful SDK test validates SQL compatibility        |

If no exposure rows appear, inspect the actual root and experiment evaluation first, including fallback diagnostics that report a missing tag. Then check the project predicate, query window and parser. If exposure exists without metrics, verify identity, event or annotation timestamps, metric filters and missing-score coverage. If a tool upgrade breaks SQL, compare the installed schema with the target schema and fix the affected query.

Large Langfuse tables may need a reviewed deduplication strategy instead of `FINAL`. Treat performance tuning as a database-specific query change: verify that it still selects the intended latest row for the correct project before accepting faster results. Changing tracker options after generation does not necessarily rewrite existing SQL; inspect saved queries and read them back after any edit.

## Rollback and verify the control

There are two controls to document. The local bypass chooses known-good behavior before experiment evaluation, independent of a stale payload. The remote feature rule controls future assignment after the service receives an updated payload. Use the local bypass first when an incident needs immediate application control, following the service's approved configuration/deployment process.

In GrowthBook, disable or remove the production Experiment rule and retain the reviewed control default. Publish only that authorized feature/environment change. Then verify the SDK payload and the running service's received revision. Stopping or archiving the analysis is not, by itself, proof that a cached SDK stopped assigning treatments.

Run one approved post-rollback request. Check the actual prompt/config value, root trace, and absence of a new experiment tag when the bypass is active. Verify that normal tracing and error reporting continue. Retain evidence from the failed treatment and its historical exposure; rollback does not undo model responses already delivered, reverse provider charges, delete traces or make prior assignments disappear.

For a telemetry-only regression, restore the previous exporter/adapter configuration or revert the bounded instrumentation change through the normal release process. Do not remove an entire shared OpenTelemetry provider or change another service's tracer project. Database privileges and generated resources can be removed later by their owner after confirming that no other experiment depends on them.

## DIY versus GrowthBook

A short offline comparison or a small internal prototype can reasonably use a local script and existing trace exports. That is often enough to find malformed prompts or measure one request's latency. Keep that smaller path when stable user assignment, ongoing experimentation and production rollout control are not requirements.

Once a team needs consistent assignment across services, repeatable exposure queries, shared metrics, guardrails and audited decisions, the homegrown responsibilities expand. GrowthBook standardizes assignment and analysis, while Langfuse or Phoenix remains responsible for recording and scoring model behavior. The integration still needs correct identity, reliable exports, maintained SQL, reviewed outcomes and engineering ownership. A platform does not remove those responsibilities or guarantee an experiment win.

## Python adaptation

<Warning>
**The Python adaptation has not been executed.** The TypeScript test results do not verify this example. Before using it, check the installed Python SDK contracts and run the same request-isolation, root-tag, failure, and staging trace-to-metric checks described above.
</Warning>

The executable fixture above is Node/TypeScript. A Python application uses the experiment-viewed callback described in the [Python tracing example](/integrations/llm-tracing#python), with a list scoped to one request. In particular, load features, **evaluate the feature**, then propagate the populated tags before opening the traced workflow. Loading features alone never invokes the assignment callback.

This small adaptation illustrates that ordering; it is not a separately executed Python fixture. Keep the tracing platform's existing Python initialization and reproduce the same concurrency, failure and root-attribute tests before claiming Python verification.

```python
from growthbook import GrowthBook

def select_prompt(user_id: str, api_host: str, client_key: str):
    tags: list[str] = []

    def on_experiment_viewed(experiment, result, user_context):
        if "=" in experiment.key:
            return
        prefix = f"gb.exp:{experiment.key}="
        tags[:] = [t for t in tags if not t.startswith(prefix)]
        tags.append(prefix + result.key)

    gb = GrowthBook(
        api_host=api_host,
        client_key=client_key,
        attributes={"user_id": user_id},
        on_experiment_viewed=on_experiment_viewed,
    )
    gb.load_features()
    prompt_label = gb.get_feature_value("support-prompt", "production")
    return gb, prompt_label, tags
```

Keep `gb` request-scoped and call `gb.destroy()` after the workflow, including its failure path. Use `propagate_attributes` for Langfuse or OpenInference's `using_attributes` for Phoenix around the root operation. Never promote this list to module state in a multi-user server. If Python is your primary stack, treat the missing independently tested Python reference as an explicit remaining task.

## Definition of done

Return a compact receipt with these fields and actual evidence:

- **Fit:** tracer server/backend, SDK versions, supported path or reject reason.
- **Contract:** feature key, experiment key, variation keys/values, identity unit, tracer project and data source.
- **Local:** files, package lock, type-check and test commands, root attributes, isolation, fallback and strict-validation results, and local-bypass evidence.
- **Staging:** approved changes, sanitized payload, analysis start time, fresh trace IDs, database readback, assignment-query rows and metric arithmetic.
- **Production:** separate key/project filters, reviewed outcomes/guardrails, authorized rollout and owner; or explicitly pending.
- **Rollback:** exact bypass/rule action and the observed control/trace result.
- **Limits:** unexecuted SQL, untested language/framework paths, missing cost/eval collection, unresolved schema/version questions and remaining operator steps.

Do not describe a local test as a completed remote integration. Do not describe a successful staging query as a verified production experiment. Preserve the last independently observed state so the next engineer can resume without repeating assumptions as facts.
