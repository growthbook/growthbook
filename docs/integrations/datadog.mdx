## Datadog with Feature Flag Data

Sending GrowthBook feature flag evaluations to Datadog lets you see which experience each user got next to the errors, latency, and sessions Datadog already records. Once flags are visible in Datadog, you can alert on them and roll flags back automatically when something goes wrong.

This guide covers the initial setup, then three ways to automate rollbacks:

1. [One monitor per flag](#option-1-one-monitor-per-flag), created by hand or by a small sync job
2. [A shared monitor with correlation logic](#option-2-shared-monitor-with-correlation-logic) that works out which flags are responsible
3. [A warehouse sync](#option-3-warehouse-sync-with-safe-rollouts) that lets GrowthBook's Safe Rollouts make the call

### Setup

#### Browser: Datadog RUM

<Info>
**Older Datadog RUM browser SDK versions**

If your Datadog RUM browser SDK version is below v5.17.0, [enable feature flags during RUM SDK initialization](https://docs.datadoghq.com/real_user_monitoring/guide/setup-feature-flag-data-collection/?tab=browser#setup).

</Info>

Report every feature flag evaluation to Datadog RUM using GrowthBook's SDK `onFeatureUsage` callback:

```javascript
const gb = new GrowthBookClient({
  onFeatureUsage: (featureKey, result) => {
    datadogRum.addFeatureFlagEvaluation(featureKey, result.value);
  },
});
```

#### Server: Datadog APM

The same callback can tag the active APM span, so every trace carries the flags that were on for that request:

```javascript
const gbClient = new GrowthBookClient({
  onFeatureUsage: (featureKey, result) => {
    tracer.scope().active()?.setTag(`feature_flag.${featureKey}`, String(result.value));
  },
});
```

With that in place you can filter or group error spans by `@feature_flag.<key>` in Datadog, which is what the rollback options below rely on.

## Automatically rolling back flags

All three options end the same way: something calls the GrowthBook REST API to roll the flag back. There are two ways to do that:

- **Kill switch.** [Toggle the feature off](/api/features-v2/operation/toggleFeatureV2) in the affected environment. Fast and blunt; users get the SDK's fallback value.
- **Revert the rollout.** [Disable the active rollout rules](/api/feature-revisions-v2/operation/putFeatureRevisionRuleV2) in a new revision and [publish it](/api/feature-revisions-v2/operation/postFeatureRevisionPublishV2). Users fall back to the value they had before the rollout, nothing is deleted, and the revision history records the alert that caused it.

The options differ in who decides which flag to roll back.

### Option 1: One monitor per flag

Datadog names the flag. Each flag you want to protect gets its own monitor comparing the error rate with the flag on against the flag off. When it fires, the alert carries the flag key, so no guessing is needed.

#### Automating monitor creation

Creating monitors by hand works for a handful of flags. To cover every rollout, let GrowthBook drive it:

1. GrowthBook triggers a “Monitor-sync” function through an [event webhook](/app/webhooks/event-webhooks) whenever a feature is published.
2. The “Monitor-sync” function creates one monitor per active rollout using the [Datadog Monitors API](https://docs.datadoghq.com/api/latest/monitors/), and cleans up monitors for rollouts that have ended.
3. Datadog triggers a “Rollback” function whenever a monitor alerts.
4. The “Rollback” function calls the GrowthBook API to trigger a rollback.

```python
# GrowthBook event webhook
onFeaturePublished(feature):
  if hasActiveRollout(feature):
    addDatadogMonitor(feature.id)
  else:
    removeDatadogMonitor(feature.id)

# Datadog alert webhook
onDatadogAlert(alert):
  flag = alert.scope["feature_flag.key"]
  rollbackRollouts(flag)
```

Tag each monitor with the flag key and group its query by `feature_flag.key`, so the alert's `$ALERT_SCOPE` names the flag (see the webhook payload in [Option 2](#option-2-shared-monitor-with-correlation-logic)).

Use this option when a warehouse export is not practical and you need to protect small rollouts (a few percent of traffic) that a shared, service-level monitor can't see.

### Option 2: Shared monitor with correlation logic

A function infers the flag. One ordinary monitor on a service's error rate fires, and the function works out which active rollouts are likely responsible before rolling them back.

1. A single shared Datadog alert triggers a function (for example, error rate above 5%).
2. The function gets all active rollouts from GrowthBook's API.
3. (Optional) The function calls Datadog's API and tries to correlate rollouts with metrics, for example by comparing the error rate with each flag on against off over the alert window.
4. The function calls the GrowthBook API and triggers rollbacks if needed.

```python
onDatadogAlert(alert):
  flags = growthbook.getAllActiveRollouts()
  for flag in flags:
    if datadog.errorRate(flag, on) > datadog.errorRate(flag, off) + margin:
      growthbook.rollbackRollout(flag)
```

Point the Datadog webhook at your function with a custom payload so the handler gets the alert's context. A useful template:

```json
{
  "alert_id": "$ALERT_ID",
  "alert_title": "$ALERT_TITLE",
  "alert_transition": "$ALERT_TRANSITION",
  "alert_scope": "$ALERT_SCOPE",
  "alert_query": "$ALERT_QUERY",
  "tags": "$TAGS",
  "date": "$DATE",
  "link": "$LINK"
}
```

Only act on `Triggered` and `Re-Triggered` transitions; `Recovered`, `Warn`, and `No Data` should be acknowledged and ignored.

Use this option if you want the fastest path to a working loop. It catches big regressions but is less sensitive to subtle issues, and a rollout at a few percent of traffic may not move a service-level monitor at all.

### Option 3: Warehouse sync with Safe Rollouts

GrowthBook decides. Datadog data lands in your warehouse as a guardrail metric, and [Safe Rollouts](/features/safe-rollouts) revert the flag automatically when a guardrail regresses. Datadog becomes a data source rather than the decision maker.

1. Datadog APM or RUM data gets synced into your warehouse, for example through Datadog's log forwarding or a scheduled export of error counts per user.
2. You define guardrail metrics in GrowthBook with SQL (for example, error rate per user) on a fact table over that data.
3. Feature rollouts query the warehouse on a schedule and run GrowthBook's stats engine.
4. If significant regressions are detected, GrowthBook rolls back automatically.

The warehouse rows need a user identifier that matches the one in your SDK's tracking callback, so errors can be joined to flag exposures. Tagging spans with the user id (for example, `usr.id`) alongside the flags makes this straightforward.

Use this option if you have a warehouse and are OK owning the ETL. It gives statistical rigor and avoids false positives, at the cost of a slower reaction time than a Datadog monitor.
