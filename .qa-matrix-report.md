### ROOT CAUSE: ramp-schedule live state writes are gated as DRAFT-class, project-scoped

This is the answer to "do content and state share a single gate?" — **yes, they share one gate, and it is draft-class.**

`packages/back-end/src/models/RampScheduleModel.ts:394-401`
```ts
protected canUpdate(existing, _updates, newDoc) {
  return this.context.permissions.canEditFeatureDrafts({
    project: this.getProject(newDoc),
  });
}
```

`packages/back-end/src/routers/ramp-schedule/ramp-schedule.controller.ts:310` `postRampScheduleAction` contains **no permission check of its own** for `pause`, `resume`, `advance`, `rollback`, `jump`, `complete`, `restart`, `start` (verified by grep: the only permission calls in the file are `canBypassFlagApprovalChecks` at :427/:467, which only guard *force*-advancing past a pending approval, and `canCreateExperimentSnapshot` at :788 for refresh-monitoring). Authorization therefore falls through to the BaseModel `update()` → `canUpdate` above.

Consequences, both directions:
1. **Over-grant**: `FlagsEditDrafts` alone lets you pause / advance / rewind / complete a **live** rollout. These are real-time writes that change what users are served right now; they never go through a revision. A draft-only author should not be able to do them.
2. **Under-grant**: `FlagsPublish` alone does **not** let you do them, even though these are publish-class live writes. There is no `canPublishFeature` anywhere in `Rule.tsx`, `RuleList.tsx`, `HoldoutRule.tsx`, `FeatureRules.tsx` or `components/RampSchedule/**`.
3. **No environment scoping at all.** `canEditFeatureDrafts({project})` is project-scoped and takes no environment argument, so the gate ignores the schedule's environments entirely. A drafter with project access can advance a schedule rolling out in `production` regardless of which environments they hold. (The vacuous-empty-array hazard does not apply here because no env array is ever passed — the issue is the total absence of env binding on a live, env-specific write.)

Front-end side, `Rule.tsx` compounds it. `canEdit = canEditFeatureDrafts(feature)` (`:429`) gates the kebab dropdown (`:822`), which is why the no-edit personas see no kebab at all. But several ramp controls sit OUTSIDE any permission gate:
- `Rule.tsx:1557` + `:1644-1678` `RampTimeline` — bare `{rampSchedule && (`, with `onJump` / `onComplete` / `onCompleteAndDisable` passed unconditionally. `RampTimeline.tsx:694-700` has no permission prop; `:395-396` derives CTA visibility purely from handler presence.
- `Rule.tsx:515-604` inline `Start` / `Approve & start` / `Resume` / `Approve Step` CTAs — no permission term.
- `Rule.tsx:609-647` `Restart` CTA, `:783-814` `RampMonitoringCTAs`, `:649-663` safe-rollout `DecisionCTA` — no permission term.

### Bugs found

**B1 — Ramp-schedule live state writes are gated as draft-class, project-scoped. CRITICAL. NOT FIXED (design decision).**
`RampScheduleModel.ts:394-401` `canUpdate → canEditFeatureDrafts({project})` is the single gate for both revision-bound schedule *content* and real-time schedule *state* (pause/resume/advance/rollback/jump/complete/restart). `ramp-schedule.controller.ts:310` has no check of its own, so all state actions authorize as draft writes. Proven both directions in the browser: qa_drafter paused and resumed a live schedule (200/200); qa_publisher holding publish on all four environments got 403. Also completely env-unscoped — the gate takes no environment argument, so a drafter can advance a schedule rolling out in production regardless of environments held. Fixing this properly means routing state actions through `canPublishFeature` with the schedule's environments, on both the model and `Rule.tsx`; too large and too design-laden for me to land unreviewed.

**B2 — Saved Group `Delete Selected (N)` ungated. Medium. FIXED.** Front-end offered it to qa_deleter; server refused (403), no stray draft. The commit that fixed Edit / Overwrite list / Add items missed this fourth sibling.

**B3 — Saved Group `Edit Information` ungated. Medium. FIXED.** Gate had no permission term at all, and its revision-status term was itself conditioned on `metadataReviewRequired`, so with metadata review off it was never disabled. Config and Constant gate this correctly.

**B4 — `Discard draft` ungated on Config/Constant/Saved Group. Medium. FIXED.** A reviewer-only, revert-only or publish-only role was offered an enabled Discard draft, which is a draft-class action.

**B5 — Publish-permission blocker styled as violet info, not amber crossed-circle. Low. FIXED.** Two sites, sitting directly above genuinely-informational callouts, so the denial was visually indistinguishable from them.

**B6 — Ungated `RampTimeline` popover CTAs. Medium. FIXED.** Every no-edit persona was offered `Jump to Step N` / `Complete ramp`; it 403'd **silently** — the popover stayed open and nothing reported the refusal.

**B7 — Drafter's "Change enabled environments" modal. Low. NOT FIXED.** All four env switches silently disabled with no tooltip and no blocker text, and `Publish now` offered as an enabled radio to a persona that cannot publish. Left alone because the intended drafter behaviour here depends on the same publish-vs-draft question as B1 — worth deciding together.
