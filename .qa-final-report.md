## BUG 1 (HIGH, browser-confirmed) -- reverter cannot land a revert on Config/Constant
Cell: qa_reverter x Config (and x Constant, same handler shape).
Repro: /configs/purchase-flow#review on the live revision -> "Roll back" (enabled) -> modal defaults to
"Publish now" -> click "Publish Now" -> red callout in modal: "You do not have permission to perform this action".
Network: PUT http://localhost:3100/configs/cfg_2CcPGE6Kt6LymXQ9qakFRQ?forceCreateRevision=1&title=Revert+to+%22Revision+1%22&revertedFrom=rev_...&autoPublish=1 -> 403
This is bug pattern #2 (button-that-fails) AND #3 (gate uses the publish atom where revert belongs).

Root cause: the direct-write path's inline landing gate required the `publish` atom unconditionally
(only a pure archive was exempt), so revert authority alone could never land a revert:
  packages/back-end/src/routers/config/config.controller.ts   (willPublish gate)
  packages/back-end/src/routers/constant/constant.controller.ts (willPublish gate)
Asymmetry proving intent (NOT a deliberate design decision):
  - RevertModal.tsx props doc: "Revert authority: landing a revert is its own atom, not publish.
    Alone it's enough to both propose and land one."
  - REVISION_PERMISSIONS has first-class `revert` atoms (revertConfigs / revertConstants).
  - Feature revert (api/features/postFeatureRevisionRevert.ts) gates strategy:"publish" on canRevertFeature.
  - The GENERIC revision publish path already does it right:
    revisionActions.ts assertCanPublishRevision = publish authority OR (revert authority AND isPureRevertRevision).
  Only the internal PUT direct-autoPublish path missed the revert fallback.

FIX APPLIED:
  - packages/back-end/src/revisions/revertPurity.ts: new `isPureRevertPatch(context, {revertedFrom,
    entityType, entityId, patchOps})` -- pre-revision analogue of isPureRevertRevision for direct-write
    paths that authorize before a revision document exists. Requires the named revision to be `merged`
    and to belong to THIS entity, then reuses proposedChangesOnlyRestore so a caller-supplied change set
    cannot front arbitrary values behind a valid revertedFrom id. Deliberately independent of the org's
    revertsBypassApproval setting (that governs skipping REVIEW, not whose authority lands the write).
  - config.controller.ts / constant.controller.ts: landing gate is now
    publish-atom OR (revert-atom AND isPureRevertPatch). Fail-closed if purity can't be proven.
  - pnpm --filter back-end type-check: PASS. eslint --fix on all 3 files: clean.
### BUG 1 -- full root cause: THREE stacked gates, not one
Re-testing after the first fix moved the error but still failed, revealing two more layers. All three
required the `publish` atom on a path a revert-only role must be able to use:
  1. ENTRY gate (config.controller.ts / constant.controller.ts): required the `draft` atom for any
     non-archive request -> a revert-only role never even entered the handler.
     Error seen: "You do not have permission to perform this action".
  2. LANDING gate (`willPublish`): required the `publish` atom (first fix).
  3. MODEL backstop: ConfigModel/ConstantModel/SavedGroupModel `canUpdate` -> canLandEntityUpdate()
     -> publish atom only. Error seen: "You do not have access to update this resource".
     Note this layer also made assertCanPublishRevision's existing revert fallback (revisionActions.ts:118)
     effectively DEAD for a revert-only role -- the generic "publish a revert draft" path would have hit
     the same backstop. So the bug was wider than the direct-write path.

FIX (all layers), files changed:
  - packages/back-end/src/revisions/revertPurity.ts
      + isPureRevertPatch(): pre-revision purity check (target must be `merged` and belong to THIS
        entity; ops must only restore its published state). Independent of revertsBypassApproval.
  - packages/back-end/src/routers/config/config.controller.ts
      entry gate: canDraftEntity OR canLandArchive OR canRideRevert (revert atom + revertedFrom named).
      + write-narrowing: a caller admitted on revert authority alone must satisfy isPureRevertPatch,
        for a DRAFT as well as a publish -- so revert authority cannot author arbitrary drafts.
      landing gate: publish atom OR (pureRevertPatch AND revert atom).
  - packages/back-end/src/routers/constant/constant.controller.ts  (identical three changes)
  - packages/back-end/src/revisions/archiveTransition.ts
      canLandEntityUpdate(): archiving stays delete-class; an ordinary write now takes the union of
      publish and revert, with the reasoning documented (same rationale as canTouchRevision's union --
      this backstop cannot tell a revert from any other write, and the caller already proved purity).

## BUG 3 (MEDIUM, browser-confirmed, NOT FIXED -- needs a judgement call)
Cell: qa_reverter x Constant, on its OWN pure revert draft (Rev 3 of gb-api-host).
Two symptoms:
  a) "Request Review" is DISABLED with no explanation, so the reverter cannot advance its own revert
     draft. (Note: the review CTA itself is CORRECT -- the back-end only lets a ONE-STEP revert skip
     review via revertsBypassApproval; a revert staged as a draft goes through the normal cycle.
     publishRevision() has no revert-bypasses-approval exemption. So the bug is the disabled CTA, not
     the presence of a review step.)
  b) The draft pane's kebab menu opens an EMPTY popover -- no Discard / Recall. A menu button that
     opens nothing. The persona spec says a reverter may "discard/recall its own" revert draft.
Root cause (read, not yet fixed): ReviewAndPublishTab.tsx line 530
  `const canDraftOrEdit = canManageDraftsEntity ?? canEditEntity;`  -- no revert term, and it gates
  BOTH the request-review CTA / discard menu AND the draft edit affordances.
The Feature pane solves this by splitting the two concepts:
  canAdvanceDraft = canEditFeatureDrafts
                 || (authoredDraft && (hasRevertAuthority || hasDeleteAuthority))
                 || (hasRevertAuthority && draftStagesRevert)
                 || (hasDeleteAuthority && draftStagesArchive);
  ...passed to the state machine as `canManageDraft`, while the draft EDIT affordances keep using the
  strict `canManageDrafts`. The generic pane has only the one strict flag for both.
NOT FIXED deliberately: widening canDraftOrEdit wholesale would also hand the reverter revision-
description edits, rebase and reopen. The correct fix introduces a separate canAdvanceDraft and threads
it to the ~4 advance/discard call sites only (707, 1131, 1260, and the draft kebab) -- a refactor of a
pane under QA that deserves a deliberate decision rather than a QA-pass edit. Reverter is NOT blocked
overall: the one-step "Publish now" revert route works.

## BUG 4 (MEDIUM, browser-confirmed, NOT FIXED) -- publisher gets a silently disabled dead-end on a draft
Cell: qa_publisher x Constant (same pane is shared with Config, so it applies to both).
Repro: admin created draft Rev 5 on gb-api-host (value foo -> foo-publisher-test). Viewed as qa_publisher.
Offered: "Request Review" DISABLED, NO publish CTA, and **no explanatory text anywhere** -- just a
disabled button and empty space. The draft kebab opens an EMPTY popover.
This is the brief's "control silently disabled with no explanation" pattern.
Why it happens: the pane renders the amber "You don't have permission to publish this draft" only when
`!canPublishOrEdit`. A publisher HAS publish authority, so that text is suppressed; the CTA is
"Request Review" (approval required + status draft) which is disabled by `!canDraftOrEdit`. There is no
helper text for missing DRAFT authority, and no menu-hiding for it either.
Same root cause family as BUG 3 -- ReviewAndPublishTab.tsx has helper text for the missing publish atom
but none for the missing draft atom. Fix belongs with the BUG 3 canAdvanceDraft refactor.
Coherence note (the question the brief asked): publish authority alone can never move an
approval-required draft forward -- it cannot request review (draft-class) and cannot approve
(review-class). That IS coherent with the documented model ("There is deliberately no 'edit'/'manage'
verb: an edit is a draft plus a publish" -- revisionPermissions.ts), but the UI explains none of it.
