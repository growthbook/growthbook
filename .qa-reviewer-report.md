### Static map of the review stack (from code read, to be verified in browser)

Architecture: Features have a BESPOKE review stack. Configs / Constants / Saved Groups share
one generic revision engine.

| Entity | FE component | FE gate | BE route |
|---|---|---|---|
| Feature | `components/Reviews/Feature/ReviewAndPublish.tsx` | `canReviewFeatureDrafts(feature)` | `POST /feature/:id/:version/submit-review` |
| Config | `components/Revision/ReviewAndPublishTab.tsx` (shared) | `canRevisionAction("config","review",config)` | `POST /revision/:id/review` |
| Constant | same shared tab | `canRevisionAction("constant","review",constant)` | `POST /revision/:id/review` |
| Saved Group | same shared tab | `canRevisionAction("saved-group","review",savedGroup)` | `POST /revision/:id/review` |

Policy atoms (`packages/shared/src/permissions/permissions.constants.ts`):
- `FlagsReview` = `["readData","reviewFeatures","reviewConfigs","reviewConstants"]`
  -> one policy covers all three flag-family entities.
- `SavedGroupsReview` = `["readData","reviewSavedGroups"]`.
Review is project-scoped for all four (`revisionPermissions.ts`), so no env binding narrows it.

The already-fixed Features logging bug: commit `b9a8d5eeec`
"fix(permissions): derive revision-log authority from the action being logged",
in `packages/back-end/src/models/FeatureRevisionLogModel.ts`. The old gate accepted only
create/edit authority, so a review-only role's log write was refused; because the write is
fire-and-forget with a swallowed `.catch()`, the verdict landed but the history entry vanished.

Static prediction for the other three: NOT vulnerable to the same class of bug, because their
activityLog append happens in the SAME `updateWithCas` transaction as `reviews[]`/`status`
(`models/RevisionModel.ts` ~943), so a verdict cannot land without its log entry. To be
confirmed empirically below — the point of this pass is not to trust that prediction.

Note: the `revisions` collection currently holds 15 `config` + 4 `saved-group` targets and
ZERO `constant` targets, so the Constant review path has likely never been exercised.

### FINDING 1 (cosmetic/UX, low severity) — disabled "Roll back" has no permission blocker

On a PUBLISHED revision's Review & Publish pane, the reviewer sees the `Roll back` button
**disabled** (correct — no revert atom) but the only accompanying text is the ordinary
informational line, in **violet with an ⓘ info icon**:

  "This revision is currently live. Rolling back reverts to the previously published revision."

There is NO amber crossed-circle blocker saying the reviewer lacks permission to revert. So the
control is disabled with no explanation of why — exactly the "blocker styled as info rather than
amber crossed-circle" pattern the brief asks about, in its missing-blocker form.

Contrast with the same pane's `Publish` button on a DRAFT revision, which does it correctly:
disabled + amber crossed-circle "You don't have permission to publish this draft."

Admin sees the same violet informational line with an ENABLED Roll back button, so the line
itself is correct copy for admins; it is just not supplemented by a blocker when the viewer
cannot revert.

**Feature Flags are NOT affected** — `components/Reviews/Feature/ReviewAndPublish.tsx:1486-1495`
already renders the amber crossed-circle "You don't have permission to revert this feature."
alongside the info line. Verified in the browser on `f1?v=6`. So this was a gap in the shared
generic pane only, affecting Config + Constant + Saved Group.

Root cause: in `packages/front-end/components/Revision/ReviewAndPublishTab.tsx`, the
read-only (merged/published/discarded) actions column disabled the Roll back / Revert button on
`!canRevertOrEdit` but its only warning was gated on `!hasAnyAuthority && !canComment`.
`hasAnyAuthority` is the UNION of draft|review|revert|publish, so a review-only role satisfies it
and the warning never rendered. The draft column already had the right pattern for publish,
with a comment stating the principle ("a greyed-out button with no reason reads as a bug").

**FIXED.** Added two blockers to that column, mirroring the Features pane and using the
`entityNoun` the callers already pass ("config" / "constant" / "saved group"):
- `revision.status === "discarded" && !canDraftOrEdit` ->
  "You don't have permission to edit drafts for this {entityNoun}."
- `revision.status !== "discarded" && onRevert && !canRevertOrEdit` ->
  "You don't have permission to revert this {entityNoun}."

`pnpm --filter front-end type-check` passes; `eslint --fix` clean.
Re-verified in the browser as the reviewer: constant now shows amber crossed-circle
"You don't have permission to revert this constant."

### Does the colleague's "a reviewer was unable to approve drafts" report reproduce?

**No. It does not reproduce on any of the four entities.**

The `qa_reviewer` persona — holding only `ReadData` + `FlagsReview` + `SavedGroupsReview` — was
able to approve AND request changes on a pending draft for Feature Flags, Configs, Constants and
Saved Groups. Every verdict returned HTTP 200, moved the revision status correctly, and was
written to the activity log attributed to Peon Greyjoy (confirmed in Mongo, not just in the UI).
The reviewer could also retract its own review on all four.

The one thing that *looks* like "a reviewer cannot approve" but is not a permission bug: on
**Saved Groups** the reviewer is offered no approve control at all when
`settings.approvalFlows.savedGroups[0].required` is false — because in that configuration
nothing ever enters pending-review; the author just publishes directly. This org had
`approvalFlows: {}`, i.e. saved-group approvals switched OFF. If the colleague was looking at a
Saved Group (or any org with that flow disabled) they would see no Approve button and could
reasonably describe it as "the reviewer was unable to approve" — but the cause is the approval
flow being off, not the reviewer's permissions. That is my best guess at what they hit, and it is
worth confirming with them before chasing anything further.
